# Assignment 8.3 "RondiTrack State": a walk-through

How to use this: go top to bottom. Each section starts with **what the brief asked for**, then **what I built**, then **the code** (click a link and the editor opens at that line), then **how I proved it**. All links are relative to this file and work in the VS Code Markdown preview (`Cmd+Shift+V`). Line numbers are as of the last commit on `feat/8.3-state`; if you edit a file they can drift.

**A 30-second summary to start with.** Three kinds of state on three kinds of page, each kept in the one place that suits it:

- **What you are looking at** (the filters) lives in the **address bar**, so a reload or a shared link shows the same thing.
- **Data from the API** is rendered by the **server** (page one) and loaded by **TanStack Query** (the pages after it), always through our own site, never straight from the browser to the API.
- **A small preference of this browser** (pinned stokvels) lives in **Zustand** and `localStorage`, and is wiped on sign-out.

The full table of "which state lives where, and why" is in the README: [Where each piece of state lives](../web-next/README.md#L248).

## Words you will need

| Word | Plain meaning |
|---|---|
| **Half-open range** | `from` is included, `to` is not. "1 to 31 October" ends exactly where "1 to 30 November" begins, so nothing is counted twice or missed. |
| **Keyset paging / page token** | Instead of "page 3", the API gives an opaque token that remembers where the last page ended. Used with a different filter it would continue from the wrong place, so the API refuses it. |
| **Server Component** | A component that runs on the server and sends finished HTML. It can read the session and call the API. |
| **Client Component** | A component (`'use client'`) that runs in the browser: for clicks, typing and local state. |
| **BFF / `/bff/`** | "Backend for frontend": small Route Handlers on our own site. The browser asks them; they ask the API with the token and return JSON. |
| **nuqs** | A library that keeps state in the URL's query string (`?from=…`) and parses it safely. |
| **TanStack Query** | A library that fetches, caches and pages server data in the browser. |
| **Zustand** | A very small store for client-only state. |

## Step 1. The API (ASP.NET Core)

**The brief:** filter contributions by a date range, bind page tokens to their filter, add an activity feed, test every rule.

### 1.1 `from` and `to` on the contribution list

- Both are **UTC instants ending in `Z`**. The parsing is strict, so a bare date, an offset or a local time is refused (the API would otherwise have to guess a time zone): [UtcInstant.cs](../Api/Common/UtcInstant.cs#L20).
- The controller reads them, refuses `from >= to`, and refuses a `memberUserId` who is not in **this** stokvel, with a message that says nothing about other stokvels: [ContributionsController.cs](../Api/Presentation/Controllers/ContributionsController.cs#L66-L76).
- The database does the comparison: `RecordedAt >= from` and `RecordedAt < to`, a half-open range: [EfContributionRepository.cs](../Infrastructure/Persistence/EfContributionRepository.cs#L132-L133).

### 1.2 Page tokens are bound to their filter

- The filter becomes a "fingerprint" stored inside the token. `from` and `to` are part of it now: [ContributionQuery.cs](../Domain/Models/ContributionQuery.cs#L19).
- A token used under a different filter is a 400 with its own code, **`page-token-filter-mismatch`**, different from a garbled token (`invalid-pagetoken`): [the check](../Infrastructure/Persistence/EfContributionRepository.cs#L151) and [the code constant](../Domain/Exceptions/Exceptions.cs#L38).

### 1.3 `GET /api/v1/me/activity`

- The endpoint: [MeController.cs](../Api/Presentation/Controllers/MeController.cs#L42).
- It starts from "the stokvels I belong to" and **every source is limited to them**, so nothing from anyone else can appear: [ActivityService.cs](../Api/Application/Services/ActivityService.cs#L44).
- Contributions, payouts and members-joined are joined into one list (`UNION ALL`) and ordered in the database: [the union](../Api/Application/Services/ActivityService.cs#L70). Paging continues strictly after the last row, with a tie-break so rows with the same time never repeat or skip: [the keyset filter](../Api/Application/Services/ActivityService.cs#L77).
- The last page's token is the **empty string** (same as the contribution list): [ActivityService.cs](../Api/Application/Services/ActivityService.cs#L112).

## Step 2. Dates, in exactly one place

**The brief:** a date range must not lose 23:30 on the last day or count the first hours of the next month; conversion in one place; tests that pass in any time zone.

**The problem in one sentence:** a person picks "31 October" on a calendar, but the database stores UTC. South Africa is UTC+2, so 31 October in South Africa is `2026-10-30T22:00:00Z` to `2026-10-31T22:00:00Z`, and getting this wrong silently loses or adds two hours of data.

**What I built:** [saRange.ts](../web-next/src/lib/saRange.ts), the **only** file that turns a calendar day into an instant.

- It relies on South Africa being **UTC+2 all year** (no daylight saving since 1944), written down in the comment at the top: [the offset](../web-next/src/lib/saRange.ts#L10).
- It uses only UTC maths (`Date.UTC`), never the computer's own time zone, so it gives the same answer on any machine.
- `to` = midnight on the day **after** the chosen last day, which is what makes the range half-open: [southAfricanDaysToUtcRange](../web-next/src/lib/saRange.ts#L67).
- Impossible dates such as `2026-02-30` are rejected, not rolled over to 2 March: [parseDay](../web-next/src/lib/saRange.ts#L25).
- The rules for the awkward cases (from only, to only, to before from) are in the comment above the function and in [the README](../web-next/README.md#L288).

**Tests:**

- 1–31 October gives exactly `2026-09-30T22:00:00Z` to `2026-10-31T22:00:00Z`: [saRange.test.ts](../web-next/src/lib/saRange.test.ts#L8).
- 23:30 on 31 October (`21:30Z`) is inside, `22:00Z` is not: [test](../web-next/src/lib/saRange.test.ts#L16).
- A single day is exactly 24 hours: [test](../web-next/src/lib/saRange.test.ts#L27).
- `2026-02-30` is refused: [test](../web-next/src/lib/saRange.test.ts#L58).
- A 23:30 contribution on 31 October is *displayed* as 31 October: [dates.test.ts](../web-next/src/lib/dates.test.ts#L7).

**Two time zones:** the script `test:tz` ([package.json](../web-next/package.json#L12)) runs the date tests with `TZ=UTC` and again with `TZ=Africa/Johannesburg`. Both pass, and the README shows both runs (the "Start at" times differ by two hours, which proves the zone really changed).

**What to say:** "I wrote the conversion once and tested it from two time zones, so it can't be right only on my laptop."

## Step 3. Contribution history with the filters in the URL

**The brief:** filters live in the URL, survive a reload and a shared link, nonsense URLs never show an error, one shared parsers file.

**What I built:**

- **One parsers file** used by the page, the controls and the Route Handler, so a filter means the same thing everywhere: [historyParams.ts](../web-next/src/lib/historyParams.ts).
  - `member` is a strict UUID: [parseAsMemberId](../web-next/src/lib/historyParams.ts#L17).
  - `from` / `to` are strict `YYYY-MM-DD` and must be a real day. nuqs's own `parseAsIsoDate` is **not** used because it gives midnight UTC: [parseAsDay](../web-next/src/lib/historyParams.ts#L27).
  - `sort` is an allow-list of the API's four sorts: [historyParsers](../web-next/src/lib/historyParams.ts#L37).
  - `clearOnDefault` (clean address when nothing is filtered), `shallow: false` (the server renders the list) and `push` (each filter is a Back step), with the one-sentence reason: [historyOptions](../web-next/src/lib/historyParams.ts#L45).
- **The nuqs adapter** wraps the whole app: [layout.tsx](../web-next/src/app/layout.tsx#L29).
- **The page.** The server reads the URL with the shared loader ([line 37](../web-next/src/app/%28app%29/stokvels/%5Bid%5D/contributions/page.tsx#L37)), checks the member belongs to **this** stokvel and otherwise falls back to "everyone" with no error ([line 53](../web-next/src/app/%28app%29/stokvels/%5Bid%5D/contributions/page.tsx#L53)), and shows an empty state, not an error, when a filter matches nothing ([line 85](../web-next/src/app/%28app%29/stokvels/%5Bid%5D/contributions/page.tsx#L85)). The whole page: [page.tsx](../web-next/src/app/%28app%29/stokvels/%5Bid%5D/contributions/page.tsx).
- **Where the dates are converted:** [apiQueryFor](../web-next/src/lib/historyQuery.ts#L15) calls `saRange.ts` (the one converter) and builds the API query.
- **The controls** only change the address bar: [HistoryFilters.tsx](../web-next/src/components/HistoryFilters.tsx#L4). While the server renders again they say "Updating the list…" using `useTransition`: [line 22](../web-next/src/components/HistoryFilters.tsx#L22).

**Proof (browser run, all HTTP 200, no error page):** `?member=banana&from=2026-02-30&to=yesterday`, an unknown member UUID, `to` before `from` (shows a short notice), `?sort=;drop` and a doubled `from`. The table is in [Filters](../web-next/README.md#L264).

**What to say:** "The server renders the list from the address, so reload, share and Back all work. Anything invalid just means 'not set', never an error."

## Step 4. Pages beyond page one, through my own site

**The brief:** later pages come through `/bff/` Route Handlers; TanStack Query pages them; keyboard-reachable "Load more"; filter changes start again; never a token under the wrong filter.

**Why `/bff/`:** the browser must never call the API's port or hold a token. So the browser asks **our** site, and our server asks the API.

- **Activity route:** checks the session first and returns a **JSON 401** (not an HTML redirect) when there is none: [route.ts](../web-next/src/app/bff/activity/route.ts#L7), [the 401](../web-next/src/app/bff/activity/route.ts#L10).
- **History route:** same session check, and it reads the filter with **the same shared parsers** as the page: [route.ts](../web-next/src/app/bff/stokvels/%5Bid%5D/contributions/route.ts#L13), [the parsers](../web-next/src/app/bff/stokvels/%5Bid%5D/contributions/route.ts#L23).
- **Shared helpers** (JSON errors, no tokens leaked): [bff.ts](../web-next/src/lib/bff.ts#L12).
- **The proxy** answers `/bff/` paths without a session with a JSON 401 instead of a redirect (it still refreshes the session for them like for pages): [proxy.ts](../web-next/src/proxy.ts#L30).

**TanStack Query:**

- The client is created **once per browser tab** with `useState`, never at module level (a module-level one would be shared between visitors on the server), and it does not retry 4xx errors: [QueryProvider.tsx](../web-next/src/components/QueryProvider.tsx#L13), [retry rule](../web-next/src/components/QueryProvider.tsx#L20).
- `useInfiniteQuery`: [usePagedList](../web-next/src/components/LoadMore.tsx#L18).
  - `initialPageParam` is the token page one ended with: [line 29](../web-next/src/components/LoadMore.tsx#L29).
  - `getNextPageParam` returns `undefined` for an empty token, which means "no more": [line 31](../web-next/src/components/LoadMore.tsx#L31).
- **Every filter value is in the query key**, plus the token page one ended with, so a new filter (or a new page one) is a fresh list: [history key](../web-next/src/components/ContributionHistory.tsx#L20), [activity key](../web-next/src/components/ActivityFeed.tsx#L33). The history list also remounts per filter: [page.tsx](../web-next/src/app/%28app%29/stokvels/%5Bid%5D/contributions/page.tsx#L94).
- **Loading more:** an `IntersectionObserver` on the end of the list ([line 74](../web-next/src/components/LoadMore.tsx#L74)) **and** a real "Load more" button for keyboards ([line 103](../web-next/src/components/LoadMore.tsx#L103)). The status line only says "That's everything" once the API's token is really empty ([line 90](../web-next/src/components/LoadMore.tsx#L90)).

**Two caches after recording a contribution:**

1. The **server's** page one is refreshed by `refresh()` in the Server Action: [actions.ts](../web-next/src/app/actions.ts#L191).
2. TanStack's **later pages** are in the browser, so the form clears them: [ContributionForm.tsx](../web-next/src/components/ContributionForm.tsx#L43).

**Proof that a token is never sent under the wrong filter:** the README shows the API's 400 for exactly that mistake and explains why the app cannot make it ([Paging](../web-next/README.md#L323)). In the browser run I decoded every page token sent to `/bff/` and checked its filter against the request: 3 requests, 0 mismatches, including after changing the order with a list already loaded.

**What to say:** "The server draws page one. When you scroll, the browser asks my own site for the next page, and my site asks the API. A page can't show up under the wrong filter because the filter is part of the cache key."

## Step 5. Pinned stokvels (Zustand)

**The brief:** Zustand the way its docs require for Next.js, nothing from the API copied into it, no hydration warnings, pins gone after sign-out.

- **A store factory, not a global store.** `createStore` from `zustand/vanilla` inside a function, so every provider gets its own store and the server never shares one between visitors: [createPinsStore](../web-next/src/lib/pinsStore.ts#L83). It is created inside `useState` in the provider: [PinsProvider.tsx](../web-next/src/components/PinsProvider.tsx#L14).
- **Only an id and a name**, never a balance, role or member list: the `Pin` type at the top of [pinsStore.ts](../web-next/src/lib/pinsStore.ts).
- **No hydration warnings.** The store has `skipHydration: true` ([line 108](../web-next/src/lib/pinsStore.ts#L108)), and the saved pins are read in an effect **after** the first render ([rehydrate()](../web-next/src/components/PinsProvider.tsx#L20)). So the server's HTML and the first browser render both show no pins and match; the pins appear a moment later.
- **Storage can't crash the app** (private window, blocked storage): [safeStorage](../web-next/src/lib/pinsStore.ts#L34). Hand-edited saved data is checked on the way in: [sanitize](../web-next/src/lib/pinsStore.ts#L70).
- **Pins are saved per person**, so the next person on the same browser never finds them: [key](../web-next/src/lib/pinsStore.ts#L28).
- **The UI:** [PinToggle (Pin / Unpin)](../web-next/src/components/PinToggle.tsx#L8) on the stokvel page, and the "Pinned" list in the sidebar on every signed-in page: [PinnedStokvels](../web-next/src/components/AppShell.tsx#L126).

**Sign-out and expired sessions (two cases, two mechanisms):**

1. **The person presses Sign out.** The sign-out Server Action runs on the server and cannot touch `localStorage`, so the button clears the pins in the browser first, then submits the action: [useClearPins](../web-next/src/components/PinsProvider.tsx#L43), used by the button at [AppShell.tsx](../web-next/src/components/AppShell.tsx#L249).
2. **The session expires or is refused.** No button is pressed, but every such session ends on the sign-in page, so that page clears all saved pins when it opens: [ClearPinsOnSignIn](../web-next/src/components/PinsProvider.tsx#L60), placed at [login/page.tsx](../web-next/src/app/%28auth%29/login/page.tsx#L49). Browser-run proof: after Sign out the keys were gone, and pins saved by hand were removed the moment `/login` opened.

**A pin for a stokvel the member has left disappears.** The signed-in layout passes the ids of the stokvels the member is in now ([layout.tsx](../web-next/src/app/%28app%29/layout.tsx#L18)), and the sidebar hides and removes pins for any other. I chose this over a link that opens a "not found" page, because a dead link on every page is worse than one missing pin. Browser-run proof: a chairperson removed a member, and on the next load the pin was gone from the sidebar and from storage.

## Questions a supervisor might ask

| Question | Short answer |
|---|---|
| Why is the date range half-open? | So adjacent ranges never overlap or leave a gap. A row exactly at midnight belongs to the day it starts. |
| Why not use nuqs's date parser? | It makes midnight UTC, which is 02:00 in South Africa, so two hours would be lost. |
| Why does the API need to bind the token to the filter? | A token continues "after this row, in this order". Under another filter it would silently skip or repeat rows. |
| Why a `/bff/` route instead of calling the API from the browser? | The browser must never hold a token or call the API's port. |
| Why is page one not in TanStack Query? | The server already has it, fresh, with no extra request. TanStack only handles what is loaded later. |
| Why Zustand for pins and not the URL or the server? | It is a small preference of this browser that the API does not know about, shared by the sidebar and the stokvel page, and it must work with no request. |
| Why `skipHydration`? | `localStorage` doesn't exist on the server. Reading it during the first render would make the browser's HTML differ from the server's (a hydration warning). |
| What happens if I sign out in one tab and have another open? | The other tab still shows the pins until it reloads. This is listed under known gaps. |
