# Assignment 9.1 "Invites, proof of payment and the safe close": a walk-through

How to use this: go top to bottom. Each section starts with **what the brief asked for**, then **what I built**, then **the code** (click a link and the editor opens at that line), then **how I proved it**. All links are relative to this file and work in the VS Code Markdown preview (`Cmd+Shift+V`). Line numbers are as of the last commit on `feat/9.1-api`; if you edit a file they can drift.

**A 30-second summary to start with.** Three features, each with the same idea: **the server decides, the screen only explains.**

- **Joining with an invite.** A person opens an invite link, reads the rules and confirms, in three steps that live in the **address bar**, so Back, a reload and the link itself all land on the right step. The API answers every guess with a clear screen, never an error page, and the preview it sends a non-member has **no member data at all**.
- **Proof of payment.** A person uploads a photo or PDF of their payment. The browser checks size and type first, but the **API checks again by the file's bytes** and has the last word. Downloads go through our own site and only the right people get the file; everyone else gets one identical 404.
- **Closing a cycle safely.** A treasurer sees exactly what closing would do (who goes into arrears and how much), worked out **by the API, never in the browser**. The close carries a `version` of what they looked at and an `Idempotency-Key`, so a change in between is refused and a double click records the arrears **once**.

The full write-up (with every API answer) is in the README: [API check (9.1)](../web-next/README.md#L361).

## Words you will need

| Word | Plain meaning |
|---|---|
| **Invite code** | A random secret (22 characters) that lets someone preview and join one stokvel. It expires after 7 days. |
| **Preview** | What the API shows someone who is **not** a member yet: the stokvel's name, rules, amount, schedule and member count. Nothing about its members. |
| **Magic bytes** | The first few bytes of a file say what it really is (a PNG always starts with the same eight bytes). Names and the browser's `Content-Type` can lie; these can't. |
| **`nosniff`** | A response header (`X-Content-Type-Options`) that stops a browser from guessing a file's type and, say, running a "PDF" as a web page. |
| **Idempotency-Key** | A unique id sent with a request. Sending the same request again with the same key returns the first answer instead of doing it twice. |
| **Version (of a close preview)** | A fingerprint of everything the preview was worked out from. If anything changes, the fingerprint changes, and a close that carries the old one is refused. |
| **Server Action** | A function that runs on the server when a form is submitted. It can use the person's session and call the API. |
| **Toast** | A small message that appears at the corner of the screen. |

## Step 1. The API (ASP.NET Core)

**The brief:** invites (create, preview, join), proof of payment (upload, replace, delete, download), a close preview and a safe close, all with tests.

### 1.1 Invites

- **A code you can't guess.** 16 random bytes from the operating system's random generator, written as 22 URL-safe characters. The code **is** the table's primary key, so two invites can never share one: [NewCode](../Domain/Entities/StokvelInvite.cs#L51), [the key](../Infrastructure/Data/StokvelInviteConfiguration.cs#L12). It lives 7 days: [the lifetime](../Domain/Entities/StokvelInvite.cs#L11).
- **Create, preview and join** are three endpoints: [InvitesController.cs](../Api/Presentation/Controllers/InvitesController.cs#L15) (create at line 15, preview at [line 41](../Api/Presentation/Controllers/InvitesController.cs#L41), join at [line 55](../Api/Presentation/Controllers/InvitesController.cs#L55)). Only this stokvel's Treasurer or Chairperson can create one; someone outside the stokvel gets a 404, the same as for a stokvel that doesn't exist.
- **The preview sends exactly nine fields.** The DTO is the contract: [InvitePreviewResponse](../Api/Application/Contracts/InviteDtos.cs#L15). `cycleLengthDays` is `null` for monthly stokvels (a calendar month has no fixed number of days).
- **Guessing is rate-limited**, per user: 10 preview or join requests a minute, then 429 with `Retry-After`: [InviteGuess policy](../Api/Common/RateLimitPolicies.cs#L16), [the limit](../Api/Common/RateLimitPolicies.cs#L34).
- **Joining can't make two memberships.** A join needs an `Idempotency-Key` (the same key replays the first answer), and the database's one-membership-per-person key lets only one of two simultaneous joins in: [the join](../Api/Application/Services/InviteService.cs#L74), [the unique-key catch](../Api/Application/Services/InviteService.cs#L91).
- **Every refusal has a stable code:** `invite-not-found` (404), `invite-expired` (410, also for a revoked code), `already-member` (409, with the stokvel's id in the problem so the screen can link to it), 429 for guessing: [the already-member problem](../Api/Application/Services/InviteService.cs#L102).

### 1.2 Proof of payment

- **The endpoint** takes `multipart/form-data` with one field named `file`: [ContributionProofsController.cs](../Api/Presentation/Controllers/ContributionProofsController.cs#L38).
- **The type is judged by the file's first bytes**, never by its name or the `Content-Type` the client sent. JPEG, PNG and PDF only: [ProofFileType.Detect](../Api/Application/Services/ProofService.cs#L156). The stored name is cleaned of paths and odd characters and gets the extension of the **detected** type: [SafeFileName](../Api/Application/Services/ProofService.cs#L176).
- **The 5 MB limit is enforced in four agreeing places**, so a valid 5 MB file gets in and anything bigger gets a clean **413**, not a dropped connection: the endpoint's `RequestSizeLimit` and `RequestFormLimits` ([line 41](../Api/Presentation/Controllers/ContributionProofsController.cs#L41)), a filter that refuses a declared size over the limit before the form is read ([RejectOversizedBody](../Api/Presentation/Controllers/ContributionProofsController.cs#L18)), Kestrel's own limit of 5 MB plus 64 KB of multipart wrapping ([Program.cs](../Api/Program.cs#L286)), and a check on the file itself ([line 48](../Api/Application/Services/ProofService.cs#L48)).
- **Who can download:** the contribution's own member and this stokvel's Treasurer or Chairperson. **Everyone else, including a plain member of the same stokvel and a treasurer of another stokvel, gets the same 404 as a contribution with no proof**, so nobody can tell whether a proof exists. The download is sent as an attachment with `nosniff` and `Cache-Control: private, no-store`: [Download](../Api/Presentation/Controllers/ContributionProofsController.cs#L100).
- **Locked once the cycle closes.** Upload, replace and delete all get 409 `proof-locked`: [the check](../Api/Application/Services/ProofService.cs#L145).
- **Contributions say what the caller may do:** `hasProof` and `canDownloadProof`, computed by the same rule as the download itself: [FlagsAsync](../Api/Application/Services/ProofService.cs#L118).

### 1.3 The close preview and the safe close

- **One function works out the arrears.** `CalculateArrearsAsync` is used by the nightly job, the preview and the treasurer's close, so the preview can't disagree with what is recorded: [CycleClosing.cs](../Api/Application/Services/CycleClosing.cs#L46), [used by the preview](../Api/Application/Services/CycleCloseService.cs#L28), [used by the close](../Api/Application/Services/CycleClosing.cs#L108).
- **The version is a SHA-256 of the calculation's inputs**, in a fixed order: the cycle, the label, the as-of date, the amount owed and, for every member counted, what they paid. It changes whenever anything that affects the result changes: [the version](../Api/Application/Services/CycleClosing.cs#L85).
- **The close is claimed exactly once.** A conditional `UPDATE … SET ClosedAt = now WHERE ClosedAt IS NULL` says who won by its row count: a second close waits for the first, then matches no row. The arrears rows and the next cycle are written in the same transaction: [the claim](../Api/Application/Services/CycleClosing.cs#L103).
- **A stale version is refused and nothing is written.** The version is re-checked **after** the claim and **inside** the transaction, so what was checked is what is written; a mismatch rolls the claim back: [the check](../Api/Application/Services/CycleClosing.cs#L109), [409 `close-preview-stale`](../Api/Application/Services/CycleCloseService.cs#L48).
- **A repeat is safe.** The same `Idempotency-Key` returns the original 200 and the arrears exist once; a different key after it closed gets 409 `cycle-already-closed`: [CloseAsync](../Api/Application/Services/CycleCloseService.cs#L35).
- **The endpoints:** preview at [CyclesController.cs line 87](../Api/Presentation/Controllers/CyclesController.cs#L87), close at [line 105](../Api/Presentation/Controllers/CyclesController.cs#L105). Treasurer or Chairperson of this stokvel only (403 for a plain member).

## Step 2. Joining in three steps

**The brief:** a three-step join where the step lives in the URL, Back and reload land on the right step, a step you can't be on yet **redirects**, the code is never asked for twice, and no member data reaches a non-member.

**The three steps** (README: [Join flow](../web-next/README.md#L459)):

| Step | Address | What it shows |
|---|---|---|
| 1. Enter the code | `/join?step=code` | A labelled input, prefilled from the address |
| 2. Check the rules | `/join?code=…&step=rules` | Name, rules, amount, schedule, member count, when the invite expires |
| 3. Confirm | `/join?code=…&step=confirm` | The name, amount and schedule again, and a "Join <name>" button |

**One function decides the step.** [decideStep](../web-next/src/lib/joinFlow.ts#L31) takes the requested step, whether there is a code and what the API said about it, and returns the step that may be shown. The page redirects whenever the answer differs from the address, so **the address always says the step on screen**: [the redirect](../web-next/src/app/%28app%29/join/page.tsx#L46). The rules, in plain words: no usable code means step 1 only; steps 2 and 3 need an invite the API accepted; an address with a code but no step (the invite link itself) means step 2. [stepUrl](../web-next/src/lib/joinFlow.ts#L39) writes the one address for each step.

**Strict URL parsers** ([nuqs](../web-next/src/lib/joinParams.ts#L10)): the code must be 1 to 64 letters, digits, `-` or `_` ([CODE_PATTERN](../web-next/src/lib/joinFlow.ts#L19)); the step must be one of the three words. Anything else counts as "not set". **Why the address:** it is the only place that survives a reload, works with Back and is what an invite link already is.

**Every API answer is a screen, not an error page.** [fetchInvitePreview](../web-next/src/lib/invites.ts#L27) turns each answer into a value: 404 → "Check the code and try again." ([line 47](../web-next/src/lib/invites.ts#L47)), 410 → "This invite has expired. Ask the treasurer for a new one." ([line 48](../web-next/src/lib/invites.ts#L48)), 429 → "Try again in N seconds." ([line 49](../web-next/src/lib/invites.ts#L49)), already a member → "You're already a member" with a link to the stokvel ([line 43](../web-next/src/lib/invites.ts#L43)). The preview doesn't carry the stokvel's id, so for that last case the link is found among the person's **own** stokvels by name: [ownStokvelIdNamed](../web-next/src/lib/invites.ts#L58).

**Never asked twice (WCAG 2.2 SC 3.3.7).** I found this one by running the flow: the address was right after pressing Back twice, but the box was empty, because the first history entry had been loaded empty. So step 1 rewrites **its own** history entry to `?code=<typed>&step=code` just before leaving: [CodeForm.tsx](../web-next/src/components/CodeForm.tsx#L30). The box reads the code from the address, so Back always shows it.

**Nothing about members reaches a non-member.** The preview itself has no such field. The page is drawn on the server ([the facts](../web-next/src/app/%28app%29/join/page.tsx#L112), [step 2](../web-next/src/app/%28app%29/join/page.tsx#L125), [step 3](../web-next/src/app/%28app%29/join/page.tsx#L148)), and the only Client Components get **only** the code, the stokvel's name (for the button) and the first key: [JoinForm.tsx](../web-next/src/components/JoinForm.tsx).

**Joining is a Server Action** ([joinStokvel](../web-next/src/app/inviteActions.ts#L34)): the person's own token, an `Idempotency-Key` the **server** wrote into a hidden field ([JoinForm.tsx line 21](../web-next/src/components/JoinForm.tsx#L21)), the button disabled while it runs ([line 49](../web-next/src/components/JoinForm.tsx#L49)). The same key stays on a retry after an unknown outcome, so one click is one join. On success it goes to the stokvel with a short toast: [the redirect](../web-next/src/app/inviteActions.ts#L64), [the toast](../web-next/src/components/FlashToast.tsx#L15).

**Focus follows the step.** Each step's heading takes focus when it appears and says "Step 2 of 3: Check the rules"; the step list marks the current step with `aria-current="step"`: [StepHeading.tsx](../web-next/src/components/StepHeading.tsx#L14).

**Signed out.** The proxy sends `/join?code=…&step=…` to `/login?next=<that address>`, and [safeNextPath](../web-next/src/lib/safeNext.ts#L8) keeps the query string while still allowing only paths on this site, so signing in comes back to the **same step and code**.

**A treasurer creates the invite** with "Create invite link" ([createInvite](../web-next/src/app/inviteActions.ts#L89)): the full `/join?code=…` link and a copy button ([CreateInviteLink.tsx](../web-next/src/components/CreateInviteLink.tsx#L13)). It shows for whoever runs the cycle ([canRunCycle](../web-next/src/app/%28app%29/stokvels/%5Bid%5D/page.tsx#L73)); the API checks again.

**Proof:**

- Every step transition, including "confirm with no valid code goes to step 1", is a unit test: [joinFlow.test.ts](../web-next/src/lib/joinFlow.test.ts). A `next` with a query string is tested in [safeNext.test.ts](../web-next/src/lib/safeNext.test.ts).
- **A browser run:** signed-out link → sign-in → same step and code; type a code, Continue, Continue, press Back twice, the code is still in the box; an unknown code, an expired code and a badly shaped code each show their message with the code kept; a double click on "Join" made **one** membership; opening the same invite again showed "You're already a member" with the link.
- I fetched the page's HTML and its server-component data **as a non-member** for all three steps and searched for member names: none.

**What to say:** "The address decides the step and one tested function decides what may be shown, so Back, reload and the invite link can't disagree. The preview was built without member data, so there is nothing to hide."

## Step 3. Proof of payment on the page

**The brief:** an upload with the browser checking first and the API checking again; every size limit agreeing; downloads through our own site, never a public link; a toast for unexpected failures that stays.

### 3.1 The upload

- **The browser's courtesy check** reads only the file's **first bytes**, never its name or `Content-Type`, and checks the size against 5 MB (5 × 1024 × 1024 bytes, the API's number): [proofFile.ts](../web-next/src/lib/proofFile.ts#L5) ([the type check](../web-next/src/lib/proofFile.ts#L13), [the whole check](../web-next/src/lib/proofFile.ts#L26)). A wrong file is explained **under the input**, before anything is sent: [ProofControls.tsx](../web-next/src/components/ProofControls.tsx#L69).
- **The upload is a Server Action**, [uploadProof](../web-next/src/app/proofActions.ts#L42). It builds the multipart body with one field named `file`; the generated type calls the file a string (OpenAPI "binary"), which the comment next to [bodySerializer](../web-next/src/app/proofActions.ts#L59) explains.
- **The API's answer decides where the message goes** ([stateFromFailure](../web-next/src/app/proofActions.ts#L22)):
  - 413 and 415 are **under the input**, in the API's words, never a toast ([lines 25-26](../web-next/src/app/proofActions.ts#L25));
  - 409 `proof-locked` and 403 are an inline message ([line 28](../web-next/src/app/proofActions.ts#L28));
  - a 5xx or no answer is an **unexpected** failure, which becomes the toast below ([line 34](../web-next/src/app/proofActions.ts#L34)).

### 3.2 Every hop's limit agrees

A file just under the API's limit must not fail on the way. The table is in the README ([Uploads](../web-next/README.md#L491)):

| Hop | Limit | What the person sees when a file is over it |
|---|---|---|
| Browser | 5 MiB, type by bytes | A message under the input; Upload stays disabled |
| Next.js proxy | buffers up to 10 MB (its default) | not reachable first: the next hop is smaller |
| Next.js Server Action | **6 MB** ([next.config.ts](../web-next/next.config.ts#L18)), above 5 MiB plus multipart overhead | a toast that stays (only reachable by getting past the browser check) |
| API | 5 MiB of file (Kestrel 5 MiB + 64 KB); type by bytes | 413 and 415 under the input |

**Proved in the real app:** a 6 MiB file and a text file renamed `.pdf` are stopped by the browser with their message; **exactly 5 MiB and 5 MiB minus one byte both uploaded**; a text file slipped past the browser check was refused by the API's 415, shown under the input; a 6 MiB file slipped past was stopped by Next's limit and showed the persistent toast.

### 3.3 The download, through our own site

- **The Route Handler** [`/bff/stokvels/{id}/contributions/{contributionId}/proof`](../web-next/src/app/bff/stokvels/%5Bid%5D/contributions/%5BcontributionId%5D/proof/route.ts#L19) checks the session (a JSON 401 if there is none), adds the person's token and **streams** the API's body straight back, so the file is never held in memory here: [the stream](../web-next/src/app/bff/stokvels/%5Bid%5D/contributions/%5BcontributionId%5D/proof/route.ts#L56).
- **The headers** are set by us again, not just passed on: `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff` and `Cache-Control: private, no-store`, and a content type we don't recognise becomes plain `application/octet-stream`: [the headers](../web-next/src/app/bff/stokvels/%5Bid%5D/contributions/%5BcontributionId%5D/proof/route.ts#L44).
- **A 404 from the API stays a 404**, with one body for every "no": [notFoundProof](../web-next/src/app/bff/stokvels/%5Bid%5D/contributions/%5BcontributionId%5D/proof/route.ts#L15).
- **The page shows the download link only where the API said it will work** (`canDownloadProof`), but the API's 404 is what protects the file: [ProofControls](../web-next/src/components/ProofControls.tsx#L77). After the cycle closes, neither replace nor remove is offered (`canChange` is false): [where it is decided](../web-next/src/app/%28app%29/stokvels/%5Bid%5D/page.tsx#L173).

**Proved as Sipho:** in Work Stokvel (where he is Treasurer) another member's proof downloads with the three headers; in Family Stokvel (where he is a plain member) the same kind of request is a **404** and the page shows no link.

**What to say:** "The browser's check is only so a person hears about a wrong file at once. The API is the one that decides, and the download is only ever reachable through my server, which asks the API on the person's behalf."

## Step 4. Closing a cycle safely

**The brief:** a confirmation that says what will happen, from the API, never calculated in the browser; no "Are you sure? OK"; no closing on a stale preview; no arrears recorded twice; focus on the safe button.

- **The preview comes through a `/bff/` route** that passes the API's answer on and is never cached: [close-preview route](../web-next/src/app/bff/stokvels/%5Bid%5D/cycles/%5BcycleId%5D/close-preview/route.ts#L9) ([no-store](../web-next/src/app/bff/stokvels/%5Bid%5D/cycles/%5BcycleId%5D/close-preview/route.ts#L25)).
- **The dialog** ([CloseCycleDialog.tsx](../web-next/src/components/CloseCycleDialog.tsx)) fetches the preview when it opens ([loadPreview](../web-next/src/components/CloseCycleDialog.tsx#L36)) and shows **skeleton rows** meanwhile ([line 108](../web-next/src/components/CloseCycleDialog.tsx#L108)), with the confirm button disabled until there is a preview. It then lists each member going into arrears, the total and the South African date the close counts up to. **Nothing is added up in the browser.**
- **The confirm button says what it does:** "Close 2026-11 and record R 600,00 in arrears", or "Close 2026-11 with no arrears" ([line 170](../web-next/src/components/CloseCycleDialog.tsx#L170)). Never "OK".
- **Focus starts on Cancel**, not on the button that does the damage, and Esc closes (Base UI's default): [initialFocus](../web-next/src/components/CloseCycleDialog.tsx#L93). While the close is running, the dialog stays open so the API's answer is seen: [the guard](../web-next/src/components/CloseCycleDialog.tsx#L76).
- **The close is a Server Action** that sends the preview's `version` and an `Idempotency-Key`: [closeCycle](../web-next/src/app/closeActions.ts#L34), with both written into hidden fields ([version](../web-next/src/components/CloseCycleDialog.tsx#L159), [key](../web-next/src/components/CloseCycleDialog.tsx#L161)).

**The key rule, in plain words.** A key belongs to **one request**. It is reused when the outcome is unknown (no answer, or a 5xx), so a retry can't record twice. It changes after any finished answer, and when the version changes, because a different version is a different request: [the rule](../web-next/src/app/closeActions.ts#L45).

**The answers:**

| API says | What the dialog does |
|---|---|
| 200 | closes, refreshes the page, toasts what was recorded ([refresh](../web-next/src/app/closeActions.ts#L82), [toast](../web-next/src/components/CloseCycleDialog.tsx#L63)) |
| 409 `close-preview-stale` | fetches and shows the **new** preview, says "Something changed since you looked…" and the treasurer confirms again with a new key ([line 87](../web-next/src/app/closeActions.ts#L87), [the refetch](../web-next/src/components/CloseCycleDialog.tsx#L71)) |
| 409 `cycle-already-closed` | a message in the dialog and a refreshed page ([line 91](../web-next/src/app/closeActions.ts#L91)) |
| 403 | the API's own message in the dialog; nobody is signed out ([line 95](../web-next/src/app/closeActions.ts#L95)) |
| no answer or 5xx | "We couldn't confirm… trying again is safe", with the same key ([line 71](../web-next/src/app/closeActions.ts#L71)) |

**Proved in the browser:** open the dialog (skeleton rows, then the list and total, focus on Cancel); Esc closes it and focus returns to the button that opened it; record a payment **behind the open dialog**; confirm → the new preview appears (R 500,00 became R 300,00) with the "changed" note; confirm again with a double click → it closed **once**, a toast said what was recorded, and the database had **exactly one arrears row** for that cycle.

**What to say:** "The preview is the API's own calculation, and the close carries its fingerprint. If anything changed, the API refuses and shows the new numbers, so the treasurer never confirms something they haven't seen."

## Step 5. Feedback: where each message goes

**The brief:** the right kind of message for each situation; a failure toast that stays and has a reference; a wrong file never in a toast.

README: [Feedback](../web-next/README.md#L524).

| Where | Used for | Why |
|---|---|---|
| Inline message under the input | A wrong file (the browser check, or the API's 413 and 415) | It belongs to that input and must stay until fixed |
| Inline message next to a form or in a dialog | A refusal about the situation: join answers, `proof-locked`, 403, a stale preview, "try again in N seconds" | The person must read it and act on it where they are |
| Short toast | Success: "Proof uploaded.", "You joined <name>.", "Closed 2026-11. Recorded R 300,00 in arrears for 1 member." | Confirms something already visible |
| Toast that **stays until closed**, with "Reference: …" | An unexpected failure of an upload or removal | Nothing the person can fix; they may need to quote the reference |
| Dialog | Closing a cycle | It can't be undone, and the consequence must be seen first |

- **The persistent toast** has no timeout and a close button: [showUnexpected](../web-next/src/components/ProofControls.tsx#L23). Its reference is the API's `correlationId`; a failure that never reached the API gets a `web-…` reference that is **also written to the server log**: [localReference](../web-next/src/lib/errorMessages.ts#L26).
- **The toast library** is shadcn's `sonner`, pinned exactly (no `^` or `~`), mounted once: [layout.tsx](../web-next/src/app/layout.tsx#L30).
- **Side effects happen right after the server answers**, not in an effect, because a successful action calls `refresh()` and the page may re-render before an effect would run: [ProofControls](../web-next/src/components/ProofControls.tsx#L43).

## Questions a supervisor might ask

| Question | Short answer |
|---|---|
| Why not send member names in the preview and just hide them? | A non-member could read them in the network response. The preview is built without them, so there is nothing to leak. |
| Why does the address hold the step? | It survives a reload, works with Back, and an invite link already is an address. State or a cookie would lose the step or break the link. |
| Why does the browser check the file if the API checks again? | So the person hears about a wrong file at once. The API is still the one that decides, by the bytes. |
| Why is the file type judged by its first bytes? | A name or a `Content-Type` is just text the sender chose. The first bytes are what the file really is. |
| Why is the Next.js limit 6 MB when the API's is 5? | So Next never refuses a file the API would accept (a 5 MB file plus multipart overhead is a little bigger). The API is the one that says no. |
| Why stream the download instead of redirecting to a storage link? | A link could be shared or cached. Through my server, every download is checked against the API for that person, and the file is never public. |
| Why the same 404 for every "no" on a download? | So nobody can tell whether a proof exists in a stokvel they don't belong to. |
| Why can't the browser work out the arrears? | Then the dialog could say one thing and the API record another. One function works it out for the preview, the close and the nightly job. |
| What stops a close on an old preview? | The `version`. It is re-checked inside the same transaction that writes the arrears; a mismatch rolls everything back. |
| What stops the arrears being recorded twice? | The close is claimed with `UPDATE … WHERE ClosedAt IS NULL`, so a second close matches no row, and the Idempotency-Key replays the first answer. |
| When is the Idempotency-Key reused and when is it new? | Reused for the same request after an unknown outcome; new after a finished answer or a new version, because that is a different request. |
| Why does a failure toast stay? | Because it is something the person can't fix and may need to quote. A toast that vanishes takes the reference with it. |

## Known gaps to mention first (it is better if you say them)

See [Known gaps (9.1)](../web-next/README.md#L534) for the full list. The main ones:

- The close's version check runs at **read-committed isolation**, so a payment landing in the last instant before the commit could still slip in.
- **Idempotency keys are held in memory in the API**, so a restart forgets them (the database's own rules still stop a second join or a second close).
- The invite preview and the join **share one rate limit** (10 a minute), so a person clicking through quickly uses a few of them.
- Pressing Back from step 2 **after signing in through an invite link** goes to the sign-in page, because it is in the history. The three-step Back test is done from a signed-in `/join`.
- Proof controls appear on the five latest contributions of a stokvel's page, not yet on the full history page.
- `npm audit` is not 0 (see above), and the **screenshots and the 3-minute recording are still to do**; the checks above were done with a scripted Chrome, not by hand.
